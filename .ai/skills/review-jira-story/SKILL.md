---
name: review-jira-story
description: Reviews any feature Jira story for dev-readiness — testable and distinct ACs, page URLs, dev-ready prototype links, and duplicated or conflicting ACs in linked, referenced and sibling tickets. For a new-page story generated by write-jira-story use review-jira-story-new-page instead.
---

## Parameters

`args` is a Jira ticket reference (e.g. `NRF2-1260`) or full URL (e.g. `https://eaflood.atlassian.net/browse/NRF2-1260`). If given a URL, take the ticket key from it.

This skill is read-only: never edit the ticket, add comments or change links.

Prerequisite: `ATLASSIAN_USER` and `ATLASSIAN_TOKEN` must be set. See [atlassian-credentials.md](../../../docs/ai/atlassian-credentials.md).


## Steps

### Step 1 — Fetch the ticket

Use `read-jira-ticket` with the ticket key. Work from the raw description text.

**If the ticket has no description, stop and alert the user** — do not run the checks against an empty description.

Note from the output: the parent key, subtasks, and the `Linked Issues` section.

### Step 2 — Gather related tickets

Build a list of related tickets to compare against in Check G. Fetch each with `read-jira-ticket`, in this priority order, and stop at 12 tickets:

1. Linked issues and subtasks (from the ticket output).
2. Ticket keys mentioned in the description (e.g. in Out of scope, Notes or Dependencies) — a ticket keyed in the description but not linked in Jira is itself a finding (Check F).
3. Sibling stories under the same parent: run `node .ai/skills/tools/jira/get-epic-issues.mjs <PARENT_KEY>`. If it fails (the parent is not an epic), carry on without siblings and say so in the report. Of the siblings, fetch only those whose summary overlaps the ticket's pages or behaviour; skip Done/Closed tickets unless they overlap closely.

If more candidates exist than the cap, list the ones you skipped in the report.

### Step 3 — Run all checks

Run every check below in full. Collect all findings before reporting — do not stop at the first issue. Give each finding a severity:

- **Blocker** — a developer or tester cannot work from the story as written (untestable AC, missing URL, non-handoff prototype, contradiction with another ticket).
- **Should fix** — works but is ambiguous, duplicated or likely to cause rework.
- **Nit** — style or hygiene.

---

#### Check A — Story basics

1. The description states who wants what and why (a user-need statement, or equivalent). Flag if missing.
2. There is an `Acceptance criteria` section with at least one scenario, written as `Given` / `When` / `Then`.
3. The ticket has a parent.
4. Any `Generated from` link points to a Confluence page. If `read-confluence-page` shows that page was modified after the date stamped on the ticket, flag it as possible drift (Should fix). If the version date can't be read, say so rather than flagging.

---

#### Check B — AC testability

For each scenario:

1. **Concrete steps.** `Given` / `When` / `Then` must name concrete conditions, actions and outcomes — a named page, a specific value, a specific destination. Flag steps too generic to pin down one pass/fail condition (`the correct behaviour occurs`, `an appropriate error is shown`, `any means such as…`).
2. **Observable outcomes.** A tester must be able to see the outcome in the UI, the network, an email or the database. Flag outcomes such as `exited from the journey` or `the system handles it` with no observable result.
3. **One behaviour per scenario.** Flag a `When` or `Then` that joins distinct triggers or outcomes with `or`, so a failure wouldn't show which one broke. Say how to split it.
4. **Initial state is reachable.** The `Given` must say how the tester gets into that state. Flag a `Given` that needs a state the story never explains (for example, a user who "previously uploaded" something, with no stated way to set that up).
5. **No placeholders** — `[url]`, `[page name]`, `TBD`, `TODO`, `to be confirmed`, or any unfilled template text.
6. **No UI or email copy inline.** Visible strings (headings, hint text, button labels, error messages, email wording) must be referenced via a prototype or design link, not quoted. Naming a page unquoted as a navigational reference is fine. The user-need statement is not a UI string.

---

#### Check C — Page URLs

Find the section that lists page URLs (usually `Page URLs`). Then compare it with the pages the ACs name, in both directions:

1. **Every page an AC names has a URL.** For each page named in a `Given`, `When` or `Then` (as the current page or as a destination), its URL must appear in the page URLs section. Flag any named page without one (Blocker — it can't be tested). Match page names loosely (case, trailing "page"), but flag a URL whose label can't be matched to the page the AC means.
   **Exception:** a scenario that states its destination path or full URL directly in the step (for example `I am redirected to /some/path`) needs no entry.
2. **No URL that no AC refers to.** Flag every listed URL whose page is not named in any scenario (Should fix — remove it). URLs listed for context only, with no AC, don't belong in the story.
3. **Labels are the page's own name.** Flag a label that is not a page name (for example one prefixed with `Change link`, or with stray punctuation inside the bold markup) and a bullet with no route.
4. **Duplicates.** Flag the same route listed twice.

---

#### Check D — Prototype links

Collect every prototype link in the description (the `Prototype` link, links in ACs, links in lists under scenarios). For each:

1. **Dev-ready.** The URL path must begin with `/handoffs`. A link without that prefix means the prototype page isn't ready for dev (Blocker). List each offending URL. This matches the check in `write-jira-story`.
2. **Not a placeholder** and a full URL.
3. **Reachable.** Fetch it with `curl -s -o /dev/null -w '%{http_code}' <url>`. Flag a 404 or other error. If the request fails for network or auth reasons, report that the link couldn't be checked — don't flag it as broken.
4. **Consistent version.** If links point at different prototype versions or folders, list them and ask for confirmation that this is intended (Nit).
5. **Error states** (question pages and forms only): an error outcome should link to the prototype error state with `?preview=1&error=<value>` (`1` for empty, `format` for invalid format), not to the base URL or inline text.

---

#### Check E — AC distinctness

Compare the scenarios against each other, pair by pair. Flag a pair when nothing in their steps would tell you which one failed if the underlying behaviour broke — for example, two scenarios with the same `Then` assertions, or a broad scenario (`page content matches the prototype`) that already covers what a later scenario asserts. Quote both headings and the colliding steps, and say whether to merge them or give an explicit distinguishing condition.

---

#### Check F — Scope, dependencies and traceability

1. **Notes ↔ ACs.** Every behaviour stated in Notes, Description or Out of scope exclusions that the story *does* own must be covered by an AC. Flag requirements with no AC. Flag ACs that assert behaviour stated nowhere else in the story.
2. **Out of scope items** that depend on another ticket should link to it. Flag an out-of-scope item with no ticket and no owner, and one that says "defined separately" or similar without a key.
3. **Referenced tickets.** Every ticket key mentioned in the description should be a Jira link on the ticket (dependency, blocks or relates). Flag any that aren't. Check that each referenced ticket actually covers what this story says it does.
4. **Open questions.** Flag any unresolved question, `TBD` or "to be decided" that the ACs depend on (Blocker if the AC can't be tested without the answer).

---

#### Check G — Duplicated and conflicting ACs across tickets

Using the tickets gathered in Step 2, compare every scenario in this ticket with the scenarios in each related ticket:

1. **Duplicate.** The same condition and the same outcome appear in both. Report both tickets and scenario headings, say which ticket should own the AC, and recommend removing it from the other or replacing it with a reference.
2. **Conflict.** The same condition has a different or opposite outcome in the related ticket (different destination, different behaviour, different copy source). Report as a Blocker.
3. **Overlap of ownership.** Two tickets both claim to build the same page, link or behaviour, or one lists as out of scope something the other doesn't claim. Report as a Should fix.

Quote the colliding steps from both tickets. If a related ticket has no ACs, say so rather than passing it silently.

---

#### Check H — Cross-cutting concerns

These are judgement calls. Report them as Should fix or Nit and say why the story might need them; don't present them as certain gaps.

1. **NFRs.** If the story adds or changes user-facing pages, the `Non-functional requirements` section should list the categories in [non-functional requirements](../../../docs/ai/non-functional-requirements.md) that apply (Accessibility; Security when there is a form or user input). A category may be omitted if the story says why. Do not list Browser & device compatibility or Page load performance — flag them if present.
2. **Data and backend.** If an AC changes what is stored, recalculated or sent (for example saving answers, creating a record, sending an email), check there is an AC or linked ticket covering the backend side and any data-catalogue update (see the `data-catalogue` skill).
3. **Analytics.** If the story adds a page, a journey step or a dropout, check whether a GA / GTM event is expected (see the `analytics` skill) and whether an AC or linked ticket covers it.
4. **Audit and security.** If the story edits user-owned data or sits behind a token or sign-in, check whether audit logging, authorisation or expiry behaviour is covered or explicitly out of scope.
5. **Journey tests.** If the story adds or changes a user journey, check for a testing note about updating the journey tests.

---

### Step 4 — Report

Return a structured report:

1. A `Context` line listing the related tickets that were compared (key, relationship) and any that were skipped or couldn't be fetched.
2. One section per check (A–H). Each is either **Pass** or a list of findings. Each finding has a severity tag, a description, and the relevant excerpt from the ticket (and the related ticket, for Check G).
3. A closing summary table counting findings by severity.
4. A one-line verdict:
   - **Fail** — one or more Blockers (give the count).
   - **Pass with comments** — no Blockers, but Should fix or Nit findings.
   - **Pass** — no findings.
