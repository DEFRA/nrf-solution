## Parameters

`args` is a Jira ticket reference (e.g. `NRF2-1185`) or full URL. If given a URL, take the ticket key from it.

This skill is read-only: never edit the ticket, add comments or change links. Review this ticket alone; do not read linked, referenced or sibling tickets.

Prerequisite: `ATLASSIAN_USER` and `ATLASSIAN_TOKEN` must be set. See [atlassian-credentials.md](../../../docs/ai/atlassian-credentials.md).

Be concise: report only problems, one short line per finding of roughly 20 words or fewer, with no filler. Add "Suggest: <fix>" only where the fix isn't obvious from the problem; keep it to a few words.

You review the ticket text only and never open the prototype. Checks that would need the prototype (whether the page has content links, how many Next page outcomes it has, which error states exist) are judged for internal consistency only: do not flag a scenario as missing on the basis of what the prototype might contain.

## Steps

### Step 1 - Fetch the ticket

Use `read-jira-ticket` and work from the raw description. Stop and alert the user if there is no description. If there is no `*Page type*:` line with `question page`, `content page`, `check your answers page`, `dropout page` or `confirmation page`, or the ACs use Given/When/Then, stop and tell the user to use `review-jira-story-new-page` or `review-jira-story` instead.

### Step 2 - Run all checks

Collect all findings before reporting.

#### Check A - Structure

The description, in this order, has:

1. `*As a*` / `*I want*` / `*So that*` lines, with the user a housing developer.
2. `*Page type*:` directly below, matching the scenarios present (see Check C).
3. `h2. Acceptance criteria` with a numbered list (`#`), one `# *<Prefix>:* <sentence>` per scenario. Flag bullets (`*`) used for the ACs.
4. `h2. Page URLs`, always present: a two-column table (page title, URL) whose first row is this page.
5. `h2. Out of scope` only if it has content.
6. `h2. Non-functional requirements` with at least one bullet.

Flag anything missing, out of order, or present but not allowed: Given/When/Then, `h3. Scenario` headings, Testing notes, Notes, Context, a "Generated from" line, a separate Prototype line, a prototype column in Page URLs.

Also flag Markdown that leaked into the Jira description: `**bold**`, `[text](url)`, `## Heading`, `- bullet`, or a table not written with `||` headers.

Every Jira ticket key in the description must be a Jira link, appear once, and differ from the ticket being reviewed. Each Out of scope item that another ticket owns must name that ticket's key.

#### Check B - AC wording

For each AC:

1. The bold prefix is a short description of the scenario, and the sentence doesn't repeat it.
2. Validation prefixes name the validation in brackets, e.g. `Form validation (missing value)`.
3. One behaviour per AC: no "or" joining pages or outcomes, no slashes in place of a word, no ambiguous "it".
4. Other pages are named by title in italics (`_Title_`), never by route or URL. Flag any application path (e.g. `/request-to-use/...`) in an AC; full external links are allowed (see item 7).
5. No content strings (hint text, button labels, error text, body copy) copied from the prototype. Page titles in italics are allowed.
6. No unfilled placeholders (`[url]`, `[page name]`), no blank "valid" where what counts as valid matters, and every AC names where a tester sees the result (a page, or content via a prototype link). Flag vague outcomes such as "the correct page", "an error is shown" or "is handled".
7. External destinations are a full link in the AC, state that they open in a new tab, and are not in Page URLs.

#### Check C - Scenario set for the page type

- **question page:** Page content, Back link, Content links (if the page has any), Next page (one per distinct outcome), Form validation (missing value, plus any other reachable error), Show saved selection. Flag a missing scenario as a comment, never a blocker.

  **Altered pages:** if the scenarios present are a clear subset of this set (for example only Back link scenarios) and every one is well formed, treat the story as one that alters an existing page. Do not flag the missing scenarios; instead note once "Altered-page story: scenario subset accepted". A missing Page content AC is then a comment, not a blocker. If the subset looks accidental (for example Page content and Back link present but no Next page on a full new-page story), flag it as a comment.
- **content page:** Page content, Back link, Content links (if any), Next page. Flag validation or saved selection scenarios.
- **check your answers page:** Page content, Back link, one Change link per summary row, Content links (if any), Next page. Flag saved selection, and any AC that describes what the destination of a change link then shows.
- **dropout page:** Page content, Back link, Content links only. Flag next page, validation or saved selection scenarios.
- **confirmation page:** Page content, Entry point (from X) per previous page, Browser back, Content links only. Flag a back link, next page, validation or saved selection scenario. Flag a missing Browser back, but not as a blocker: its destination can't be inferred from a prototype.

Flag a scenario set that doesn't fit the `*Page type*:` line.

#### Check D - Prototype links and Page URLs

1. The Page content AC links a prototype. Flag a missing link as a **Blocker** (unless the story is an altered-page story, where it is a comment). A prototype link whose path doesn't begin with `/handoffs` is a comment only: the writer warns about this and continues, so don't block on it.
2. Each Form validation AC links a prototype error state (`?preview=1&error=1`, or `error=<value>` for a specific validation). Flag an error AC that quotes error text or links without the query string.
3. Every page named in an AC (back link, next page, entry point, content link, browser back) is a row in Page URLs, and every row other than the first is named in an AC.
4. Each URL is a plausible application path starting with `/`, and each page title appears only once.

#### Check E - NFRs

Using [non-functional requirements](../../../docs/ai/non-functional-requirements.md), check every category mapped to the ticket's page type is a linked bullet. Flag a missing category unless a note explains the exclusion. Flag Security on a content, dropout or confirmation page, and Browser & device compatibility or Page load performance anywhere.

#### Check F - Distinctness

Look only for two ACs that would pass or fail together, so that a failure wouldn't show which one broke (wording problems within a single AC belong to Check B). When flagging an overlap, quote both prefixes and say whether to merge them or add a distinguishing condition.

### Step 3 - Report

Use exactly this structure. Omit any section with no findings (don't write "Pass" for it) and list the omitted sections on the last line.

```
## <KEY> - <summary>
Page type: <copied from the ticket's `*Page type*:` line, not inferred>

### Structure
- [**Blocker** - ]<element> - <problem, in a few words>[. Suggest: <fix>]

### Wording
- [**Blocker** - ]<AC prefix> - <problem>. Suggest: <fix>

### Scenario set
- <missing or unexpected scenario>[. Suggest: <fix>]

### Links and Page URLs
- [**Blocker** - ]<AC prefix or row> - <problem>. Suggest: <fix>

### NFRs
- Missing: <category> - no exclusion note

### Distinctness
- <AC prefix> / <AC prefix> - <overlap>. Suggest: <merge / distinguishing condition>

Verdict: <Fail (n blockers) | Pass with comments | Pass>. Nothing to report for: <omitted sections>.
```

Mark a finding **Blocker** only where a developer or tester cannot work from the story as written: a missing required element, a page named in an AC with no Page URLs row, a placeholder, an untestable AC, or a missing prototype or error-state link. List blockers first within each section.

Verdict: `Fail` if any blockers; `Pass with comments` if findings but no blockers; `Pass` only if there are no findings.

Do not add a summary table, a per-check pass list, or any text beyond this structure. If a section has more than 10 findings, list the 10 most important and add "+N more".
